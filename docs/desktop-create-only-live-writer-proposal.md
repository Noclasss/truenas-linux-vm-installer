# Ubuntu Desktop create-only writer: smallest implementation slice

**Status:** proposal only; this branch contains no live writer, adapter, allowlist change, or TrueNAS operation. Based on combined PR head `62177de59b556c202e2dcf42d0fe17e7a81785ad`. Keep `LIVE_PROFILE_ALLOWLIST` empty and the public `install.sh`/preview bootstrapper preview-only.

## Existing contracts to reuse

- `planning.preview.build_plan()` validates explicit values and emits `apply_supported: false`, `vm.start: false`, and `vm.autostart: false`. Desktop preview leaves `desktop_source_id` unset.
- `planning.readonly_preflight.run_read_only_preflight(client, fixture, request)` checks exact build/schema and caller-selected resources. Its read allowlist is `pool.query`, `pool.dataset.query`, `vm.query`, `vm.device.query`, `vm.device.nic_attach_choices`, `vm.supports_virtualization`, `vm.maximum_supported_vcpus`, and `vm.get_available_memory`; `verify_runtime_compatibility()` first calls `system.version` and `core.get_methods`. It does not authorize writes.
- `planning.desktop_write_contracts.build_desktop_write_intents(request, fixture, vm_id, shared_parent_exists)` validates candidate request shapes against the sanitized `TrueNAS-26.0.0-BETA.2` fixture. Candidate writes are `pool.dataset.create` (FILESYSTEM parents and VOLUME zvol), `vm.create`, and `vm.device.create` (disk, installer CD-ROM, NoCloud RAW disk, NIC); it also returns a `vm.start` intent. Schema validation is not live acceptance evidence.
- `planning.desktop_deploy_mock.rehearse()` runs a non-persistent in-memory sequence against the exact `FakeBackend` and requires `confirmation="CREATE"`. `planning.desktop_ownership.rehearse_persistent()` journals a UUID, request, planned paths, pre-existing shared-parent state, pending intent before a fake write, and verified acknowledgements after exact fake inventory read-back. `inspect_recovery()` is read-only and always refuses continue/delete. Both require exact fake backend types; neither is a live adapter.
- `planning.desktop_integrity.verify_desktop_artifacts(iso, manifest, signature, keyring)` verifies caller-supplied local ISO bytes, signed checksum manifest, size and pin. `planning.desktop_autoinstall.build_desktop_seed_image()` writes a 2 MiB private CIDATA VFAT image from user-data/meta-data. These helpers do not download the Desktop ISO or stage either file on TrueNAS.
- `planning.ubuntu_server.ubuntu_server_stage_paths_from_dataset_rows()` is a lexical, exact-row mountpoint helper for Server filenames, not a Desktop staging writer. `MidcltClient` is local `midclt` subprocess access; no remote upload interface exists.

## Proposed live boundary and exact calls

1. A future `DesktopCreateOnlyWriter` takes an already validated request, a fresh exact-build `SchemaCheckedClient`, a verified artifact/seed pair, an explicit target selection, and a durable manifest path. It must not be callable from `install.sh`, the preview bootstrapper, or preview CLI. No dynamic `profile` flag is added to the public launcher.
2. Re-run the exact-build and full read-only preflight immediately before confirmation/write. Use only the read-only method set above, the reviewed request/return fixture, explicit pool/bridge/VM choices, the current name/path conflict scan, and caller-selected reserves. Any build, schema, capacity, bridge, collision, stale-state, or artifact/seed failure aborts before the first TrueNAS mutation.
3. After a second display of the exact plan, require a fresh confirmation bound to the VM name and plan digest (the fake's bare `CREATE` is not sufficient live confirmation). Apply only these write methods, in order: `pool.dataset.create` for any missing shared parent and the new per-VM FILESYSTEM dataset; `pool.dataset.create` for the new VOLUME zvol; `vm.create` with the reviewed Desktop payload (`autostart: false`, display enabled, UEFI, Secure Boot disabled); then `vm.device.create` for the VIRTIO zvol, installer CD-ROM, and NoCloud RAW disk. Include `vm.device.create` for a NIC only after an explicit bridge selection; the proposed first disposable test omits a NIC. **Do not call `vm.start`, `vm.stop`, `vm.device.delete`, `vm.device.convert`, or any network mutation in this slice.**
4. Guard each call with the runtime schema checked client and an allowlist exactly limited to `pool.dataset.create`, `vm.create`, and `vm.device.create`. Keep the live profile allowlist empty until separately approved release gates; the helper and fake do not change that flag.

## Staged ISO and seed access

- Download the pinned ISO to a mode-0700 private local cache with bounded HTTPS transfer and the fixed digest/size, then run `verify_desktop_artifacts()` over the actual downloaded ISO, signed manifest, signature, and reviewed keyring. Reverify the bytes at the final staged destination before attaching; prior verification of a different cached file is not a staging authorization.
- Build the NoCloud image locally using the existing password-hash and VFAT helpers. Never put plaintext credentials in argv, logs, the manifest, or a public test fixture. Treat the seed contents as secret-bearing data even though the password is hashed.
- Add one narrow Desktop stage-path helper: take exactly one `pool.dataset.query` row for the newly created FILESYSTEM dataset, require the expected dataset ID/type and canonical mountpoint under `/mnt/<selected-pool>/`, and derive only `ubuntu-installer.iso` and `cidata.img`. Refuse symlinks, existing destinations, traversal, an unexpected mountpoint, or a path outside the selected pool. Copy with exclusive creation, bounded chunks, flush/fsync, and read-back of exact size/SHA-256; do not shell out to `cp` or accept arbitrary paths.
- The only existing adapter is local `midclt`; therefore this design can stage onto `/mnt/...` only when the future process is deliberately run in an authenticated TrueNAS host shell with those paths available. No remote upload method or egress policy is implemented here. Prove target-path writability and libvirt readability on the separately authorized disposable target before claiming this path works. CD-ROM ownership handoff has limited Beta.2 source evidence; RAW seed access/ownership after attachment is **not verified**. Do not guess with `chown`/`chmod`; if exact post-attach access/read-back cannot be established, stop in manual-reconciliation state.

## Durable ownership and ambiguity rules

- Extend the fake ownership format before live use (versioned v2): include a run UUID; exact request/build/plan digest; whether the shared parent existed before; explicit rows for each created dataset/zvol/VM/device and staged file (fixed path, SHA-256, byte count, intended/observed owner and mode); stable middleware IDs; ordered acknowledgements; and at most one pending `{method, identifier, request_digest, state}` intent. Keep the manifest private and atomic using `installer_core.safe_filesystem`.
- Never claim an existing shared parent. Record intent durably before each API or stage write. After a successful response, re-query exact rows and relationships (dataset ID/type/size/mountpoint; VM ID/name/disk/CPU/memory/autostart/state; device ID/VM ID/dtype/path/options; staged file identity/hash/mode/owner) before marking the step acknowledged.
- Any exception/timeout after a request may have reached TrueNAS is ambiguous: persist/retain the pending intent where possible, do not retry, resume, compensate, delete, start, or claim ownership. A read-only recovery pass may match only exact IDs, relationships and content; any mismatch, missing response, changed path, unknown ownership, or failed read-back becomes `reconcile_required` for human review. If the manifest cannot be safely written before a mutation, do not mutate.
- No automatic cleanup is part of create-only. User-reviewed cleanup is a later, separately authorized slice.

## Gaps to close before implementation can be enabled

1. The persistent fake currently models a separate `display` device and 9 acknowledgements, while the write-intent builder uses `vm.create.ensure_display_device=true` and has no separate display `vm.device.create`; reconcile this fake/contract mismatch first. The builder also includes `vm.start`, which the create-only adapter must exclude explicitly.
2. There is no Desktop downloader/final-destination stage helper, no runtime-access proof for the Desktop RAW seed, no live writer, and no live ownership/recovery adapter. The current v1 fake recovery report cannot reconcile filesystem file ownership or TrueNAS inventory.
3. The Beta.2 fixture is schema evidence only. Reconfirm `system.version` and exact runtime method contracts on a separately authorized test host; schema match does not prove writes, file access, successful installation, shutdown, or graphical login.

## Acceptance criteria for the next code slice

- Tests prove the public launcher and one-line bootstrapper cannot reach the writer; `LIVE_PROFILE_ALLOWLIST` stays empty; no start/stop/delete/convert/network call exists in the live write allowlist.
- Every invalid/missing/mismatched preflight field, contract, signature, size/hash, source ID, mountpoint, permission, conflict, reserve, confirmation, or manifest precondition produces zero TrueNAS write calls and no target-file overwrite.
- A fake adapter records each exact method/params tuple and returns stable IDs; read-back mismatches stop before the next write. A lost response after every mutation leaves a pending record, performs no retry/rollback/delete/start, and recovery only reports/manual-flags the state without writes.
- Files are staged only under the exact per-VM dataset row, with no overwrite, and their final contents match the fixed ISO/seed hashes and expected size. The seed is mode 0600 before attachment; actual libvirt read access must be independently proved before attaching it on the disposable host.
- No live allowlist change or public CLI wiring occurs in this implementation slice. Live write acceptance requires a distinct, explicit authorization, a specific disposable target/configuration, and read-back evidence.

## Disposable-test proposal (not selected or authorized)

Suggested first guest profile: exact Beta.2 test build; user-selected non-boot pool and unique VM name; 2 vCPU, 6144 MiB RAM, 32 GiB virtual disk; source `ubuntu-desktop-minimal`; UEFI, Secure Boot off, autostart off; no NIC for the first local install/GUI check; one-time local test account only. The writer would leave the VM stopped. Starting it, validating poweroff/installer behavior, or adding an isolated NIC requires a later separately scoped authorization.

Free-space floor is `disk bytes + 6,484,506,624 bytes (pinned ISO + 2 MiB seed) + caller-selected reserve`; with the suggested 32 GiB disk and a *proposed, not confirmed* 1 GiB reserve, the computed floor is 41,917,986,816 bytes. Pool, VM name, target, test credentials, reserve, source selection, network, and any live-operation permission remain unconfirmed.
